为什么用 uint8 而不是直接用 float8？

PyTorch 的 Tensor.index_put 操作不支持 torch.float8_e4m3fn 类型。

所以 SGLang 将 KV Cache buffer 分配为 torch.uint8（与 FP8 同为 1 字节）， 存取时通过 .view(dtype) 在 uint8 和 float8 之间零拷贝转换。

读取时：k_buffer[layer_id].view(self.dtype) → 得到 float8 视图。

写入时：cache_k.view(self.store_dtype) → 转为 uint8 后存入。

量化的数学操作

写入时的量化公式：cache_fp8 = (cache_bf16 / scale).to(fp8)

• div_(k_scale)：将 bf16 的 K 值除以缩放因子，映射到 FP8 的表示范围

• .to(torch.float8_e4m3fn)：PyTorch 原生的类型转换，截断到 FP8 精度

• .view(torch.uint8)：零拷贝的位模式重解释，便于 index_put 写入 buffer

kernel 内部如何处理 FP8？

FlashAttention v3 (Hopper架构) 原生支持 FP8 输入：

• K/V 以 FP8 格式直接从 HBM 加载到 SRAM，减少一半显存带宽

• kernel 接收 k_descale 和 v_descale 参数

• 在 SRAM 中进行矩阵乘法前，将 FP8 值乘以 descale 因子恢复到真实值

• 最终输出仍为 bf16/fp16 精度

注意：当 head_dim > 256 或使用 FA4 时，不使用 FP8 kernel 路径。

数据流总结

完整类型变换链：

CLI "fp8_e4m3" → ServerArgs.kv_cache_dtype = "fp8_e4m3" (str) → ModelRunner.kv_cache_dtype = torch.float8_e4m3fn (torch.dtype) → KVCache.dtype = torch.float8_e4m3fn (逻辑类型) → KVCache.store_dtype = torch.uint8 (存储类型，绕过 index_put 限制) → k_buffer / v_buffer [num_tokens, num_heads, head_dim] × num_layers (GPU 显存) 写入: bf16 K/V → div_(scale) → .to(fp8) → .view(uint8) → buffer 读取: buffer → .view(fp8) → FA kernel + descale → bf16 output

关键优势：FP8 KV Cache 将每个元素从 2 字节 (bf16) 压缩到 1 字节， 显存占用减半，意味着同等显存下可以支撑约 2x 的 context length 或并发请求数。
