NCCL Inspector

作业内 / 实时 / 常驻的 NCCL 可观测性
为什么需要（Why）
  • 通过低开销的作业内 NCCL 可观测性，加速 AI 工作负载的性能调试
  • 支持 profiling —— A/B 性能对比或与理论峰值（SOL）对比，配合集中式分析和异常检测
是什么（What）
  • NCCL 传输无关的 profiling 框架（适用于 NVLink、IB/RoCE、EFA、TCP 等所有传输方式）
  • 常驻开启，开销极低（约 0.5–1%），采样频率可调，分析与数据采集解耦
如何工作（How）
  • NCCL Inspector 按 per-comm、per-collective、per-msgsize 三个维度采集性能和状态数据
  • Timer 追踪内核启动和完成事件
  • 集合通信元数据（size、comms、序列号等）
  • 数据采集与分析后端分离
路线图（On Roadmap）
  • 按需开关事件 规划中
  • Device API 支持 规划中

内容总结

  • NCCL Inspector 是一个常驻运行、实时采集的 NCCL 性能可观测性框架，专为生产环境中的 AI 训练工作负载设计。
  • 核心定位 —— 低开销常驻监控：开销仅 0.5–1%，采样频率可调，允许在生产作业中始终保持开启，而非仅在调试时临时启用。数据采集与分析后端解耦，采集不阻塞通信。
  • 传输无关：无论底层使用 NVLink、InfiniBand、RoCE、EFA 还是 TCP，Inspector 都能统一采集，无需针对不同传输方式使用不同工具。
  • 三维度采集：
    • per-comm — 按通信器粒度，区分不同通信组的行为
    • per-collective — 按集合操作类型（AllReduce / ReduceScatter 等）分类
    • per-msgsize — 按消息大小分桶，识别不同数据量级下的性能特征
  • 右侧图表解读：对比两个作业在 NVLink ReduceScatter 操作上的内核总线带宽。Job 2311328 稳定在 ~280–300 GB/s（376.48 TFLOP/s/GPU），而 Job 2310073 仅 ~70–90 GB/s（370.83 TFLOP/s/GPU）。虽然两者计算性能接近，但通信带宽差异 3–4 倍——这种"计算正常但通信异常"的问题正是 Inspector 能快速定位的典型场景。
  • 路线图功能：未来将支持按需开关特定事件的采集（减少不需要时的开销），以及 Device API 支持（在内核级别采集通信指标）。
