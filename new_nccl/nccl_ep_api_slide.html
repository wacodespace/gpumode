内容总结

一、什么是 NCCL EP

  • EP = Expert Parallelism（专家并行），是 Mixture-of-Experts (MoE) 模型中将不同 expert 分布到不同 GPU 上的并行策略。
  • NCCL EP API 是 NCCL 新增的原生 Expert Parallelism 通信接口，提供统一、功能完备的 API 来处理 MoE 模型中的 All-to-All 通信模式。

二、原生栈 — 从应用到硬件的完整路径

  • 入口 API — 只有两个核心函数：ncclEpDispatch()（将 token 分发到对应 expert 所在的 GPU）和 ncclEpCombine()（将 expert 处理后的结果收回）。
  • 双内核策略 — 内部自动选择低延迟内核（源自 DeepEP，适合小批量 / 推理场景）或高吞吐内核（源自 Hybrid-EP，适合大批量 / 训练场景）。
  • 传输层 — 跨节点走 NCCL GIN（GPU-Initiated Networking）通过 IB / RoCE / SPC-X 进行 RDMA 通信；节点内直接使用原生 NVLink / PCIe 代码。

三、两级资源管理 — Group 与 Handle

  • Group 级别（模型生命周期） — 通过 ncclEpCreateGroup() 创建，与模型绑定，网络配置一次锁定（拓扑发现、路径分配等重开销只做一次）。
  • Handle 级别（每次前向传播） — 通过 ncclEpCreateHandle() 创建，路由状态（哪些 token 发往哪些 expert）按每次前向传播即时重建，因为 MoE 的路由决策每次都不同。
  • 设计哲学 — 将"昂贵的一次性初始化"与"轻量的每步路由"分离，摊销初始化开销，避免每个 forward pass 都重新建立连接。

四、丰富的张量语义 — ncclNDTensor_t

  • 不再是"一块裸内存" — NCCL EP 引入 ncclNDTensor_t 结构体，让通信层理解张量的形状和含义。
  • N 维 Shape & Strides — 支持任意维度描述，可以表达 [batch, seq, hidden] 等多维布局。
  • 数据类型 — 原生支持 FP32、BF16、FP8，通信层可据此优化传输和归约精度。
  • 语义标签 — 通过 TOKENS、TOPK_IDX、TOPK_WEIGHTS、SCALES 等标签标识每个张量的语义角色，NCCL 内部可据此做差异化优化（如 index 用整型传输，weights 用低精度压缩）。

五、核心价值

  • 统一替代碎片化方案 — 之前各框架自己实现 All-to-All（DeepEP、Hybrid-EP 等），现在 NCCL 原生集成，一套 API 适配所有框架（PyTorch / vLLM / SGLang / Megatron-Core）。
  • 自动选择最优策略 — 根据场景自动在低延迟和高吞吐内核之间切换，开发者无需手动调优。
  • 语义感知通信 — 张量带有类型和语义信息，NCCL 可以针对不同数据做定制化的传输优化，而非盲目搬运字节。
NCCL EP = MoE 模型的原生通信层：两个 API 搞定 token 分发与收回，
两级资源管理分离初始化与路由开销，张量语义让通信层"看懂"数据。
