缓存复用模式 (Cache Reuse Pattern)

① 检查 GPU
HIT → 继续生成（零开销）
Miss ↓
② 检查 CPU / NVMe
HIT → 注入回 GPU 后继续
Miss ↓
③ 检查 Global Store
HIT → 加载到 CPU 再注入 GPU
Miss ↓
④ 全部 Miss → 重新计算 Prefill
Cache Hit → TTFT 降低 30-60%
复用 >>> 重算

降低 TTFT（首 Token 延迟）

避免对重复上下文做昂贵的 Prefill 重计算。相同 system prompt、多轮对话等场景直接复用 KV cache，用户感知延迟大幅降低。

改善 TCO（总拥有成本）

通过缓存局部性和跨请求共享，最大化硬件利用率。GPU 算力集中在真正需要计算的新 token 上，而非反复计算相同的上下文。

内容总结

一、核心问题：GPU 显存装不下所有 KV Cache

  • 长上下文时代 — 128K、1M 甚至更长上下文窗口下，单个请求的 KV cache 可达数 GB，GPU HBM 容量成为瓶颈。
  • 重复计算浪费 — 同一 system prompt（如 "你是一个代码助手..."）每个请求都要做一遍 Prefill，算力被浪费在重复工作上。
  • 解法 — 像 CPU 的 L1/L2/L3 缓存一样，构建多层级的 KV cache 存储层次结构，热数据在 GPU，温数据在 CPU/NVMe，冷数据在集群共享存储。

二、三层存储设计

  • 第 1 层 GPU HBM — 最热工作集，仅放当前批次正在生成的 token 对应的 KV cache。容量小（80-160GB）但带宽极高（~3.5TB/s），是推理引擎直接读取的层。
  • 第 2 层 CPU DRAM + NVMe — 节点本地的温热存储。近期请求的 KV cache 卸载到这里（通过 NIXL 异步传输），命中时可以快速注入回 GPU。DRAM 约 200GB/s，NVMe 约 25GB/s，容量可达数十 TB。
  • 第 3 层外部存储 — 全集群共享的 Global KV Store，PB 级容量，通过 UCX / RDMA 访问。存放可归档和跨节点复用的 KV cache（如公共 system prompt 的 cache、用户历史对话的 cache）。

三、缓存复用逻辑

  • 类似 CPU 缓存的多级查找：先查 GPU → miss 则查 CPU/NVMe → miss 则查 Global Store → 全 miss 才重算 Prefill。
  • TTFT 降低 30-60% — 只要在任意一层命中，就可以跳过对应部分的 Prefill 计算，直接用缓存的 KV。
  • "复用远优于重算" — 从 CPU DRAM 注入 KV cache 到 GPU 的速度（~200GB/s）远快于在 GPU 上重新做 Prefill 的时间（需要完整的前向传播）。

四、关键技术组件

  • NIXL（NVIDIA Inference Xfer Library） — 负责 GPU ↔ CPU/NVMe 之间的异步数据传输，在推理生成过程中后台卸载/加载 KV cache，不阻塞推理流水线。
  • UCX / RDMA — 用于节点间的远程内存访问，支撑 Global KV Store 的跨节点数据传输。
  • Cache 索引与匹配 — 需要高效的哈希/前缀匹配机制来判断"这个请求的上下文是否有对应的已缓存 KV"。

五、典型应用场景

  • 多轮对话 — 用户第 2 轮对话时，第 1 轮的 KV cache 还在 CPU/NVMe 上，直接注入 GPU 继续，无需重做 Prefill。
  • 共享 system prompt — 千百个请求用同一个 system prompt，其 KV cache 存在 Global Store 中被所有节点复用。
  • 长上下文推理 — 128K+ 上下文不可能全放在 GPU HBM 里，分层存储让"无限上下文"成为可能。
三层存储（GPU HBM → CPU/NVMe → 集群共享存储）构建 KV Cache 的"缓存金字塔"，
逐级查找、命中即复用 — TTFT 降低 30-60%，GPU 算力只花在真正需要计算的新 token 上。
