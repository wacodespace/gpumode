内容总结

一、问题背景

  • 传统 NCCL 集合通信（Default 模式）需要 CPU 和 GPU 协作 — GPU SM 负责数据搬运，但跨节点 RDMA 通信时需要 CPU 作为 proxy 来操作网卡的 Work Queue 和 Doorbell，引入 PCIe 往返延迟。
  • SM 被通信占用意味着计算吞吐下降 — 在计算密集的大模型训练中，通信占用的 SM 不能用于矩阵计算，这是一个核心矛盾。

二、Symk 模式 — 消除 CPU 瓶颈

  • 核心思想 — 让 GPU SM 直接操作网卡的 WQ / DBR / CQ，通过 GPU 端 MMIO 直接触发 NIC Doorbell，完全绕过 CPU proxy。
  • 命名由来 — "Symmetric Kernel" 指所有 GPU 运行相同的对称内核，每个 rank 同时既是发送方也是接收方。
  • 优势 — 消除 CPU↔GPU 的 PCIe 往返延迟，实现最低通信延迟，特别适合推理场景和小消息通信。
  • 额外能力 — 支持自定义内核 hook，用户可以插入自己的通信逻辑。

三、Zero-SM 模式 — 释放全部 SM 给计算

  • 核心思想 — 通信操作完全不占用 SM：NVLink 通信由 GPU 的 CE（Copy Engine / DMA 引擎）执行，使用 TMA（Tensor Memory Accelerator）变体；RDMA 通信退回 CPU proxy 模式。
  • 优势 — SM 100% 留给计算 kernel（如 GEMM），通信和计算完全重叠，最大化计算吞吐。
  • 代价 — CE 的灵活性不如 SM（不能做复杂的 reduce 操作），且 RDMA 路径仍需 CPU 参与，所以延迟不是最优。
  • 适用场景 — SM 资源极度紧张的大模型训练，通信延迟可以被计算时间掩盖的场景。

四、CPU 准备阶段的决策逻辑

  • 模式选择 — CPU 端在入队时决定使用 regular / symk / ce 三种模式之一，通常由环境变量或 NCCL 内部启发式算法自动选择。
  • 参数选择 — 确定算法（algo：如 Ring / Tree / NVLS）、协议（protocol：如 Simple / LL / LL128）、块数（nBlocks）等执行参数。
三种模式解决不同瓶颈：Default 最通用但有 CPU 延迟，
Symk 绕过 CPU 实现最低延迟，Zero-SM 把全部 SM 还给计算 — 各取所需。
