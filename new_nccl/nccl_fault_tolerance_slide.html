内容总结

一、方案一：通信器弹性 (Communicator Elasticity)

  • 目标 — 故障不停训：当集群中某些节点 / NIC / 链路出故障时，不需要杀掉整个训练任务，而是动态调整通信器继续运行。
  • 故障检测 — 由 RAS（Reliability, Availability, Serviceability）子系统负责，检测 NIC 故障、掉队节点（Straggler）、链路错误，并通过超时和重试机制上报到框架层。
  • 三个核心 API：
    • • ncclCommRevoke() — 撤销（作废）当前通信器，让所有 rank 知道发生了故障
    • • ncclCommShrink() — 缩小通信器，剔除故障节点，用剩余健康节点重建
    • • ncclCommGrow() — 扩大通信器，加入新的替换节点
  • 典型流程：检测到故障 → 应用逻辑决定策略 → Revoke 旧通信器 → Shrink 剔除坏节点 或 Grow 加入新节点 → 任务继续。

二、方案二：快速重启 + 检查点 (Fast Restart + Checkpoint)

  • 目标 — 缩短重启时间：当故障严重到必须重启时，尽量减少重启的开销。
  • NCCL 自动处理的部分：负载均衡、冗余端口故障转移、RAS 信息提供。这些不需要应用干预。
  • 关键 API — ncclCommInitRackScalable()：大规模优化的初始化函数，跳过不必要的全局拓扑发现，按机架 (Rack) 粒度快速建立连接。
  • CUDA Communicator Checkpoint（即将推出）：将模型状态 + NCCL 通信器状态打包到一个 checkpoint 文件中，重启时直接恢复通信器状态而非重建，将恢复时间从分钟级压缩到秒级。

三、两种方案的关系

  • 互补而非互斥 — 小范围故障（一块 NIC 挂了）用弹性方案热切换，大规模故障（整个机架掉电）用快速重启。
  • RAS 是共同基础 — 两种方案都依赖 RAS 子系统提供的故障信息来做决策。
  • 降低训练中断成本 — 在万卡级集群训练中，硬件故障是常态而非异常，这两种方案将"训练中断 = 从头来"变为"秒级恢复继续"。

深入：RAS 如何定位故障传播中的根因 Rank

一、故障传播的本质 — 为什么一个节点挂了全部报错

  • 集合通信是全员阻塞操作 — AllReduce / AllGather 等操作必须所有 rank 都参与才能完成。任何一个 rank 卡住，其余 rank 全部阻塞等待，最终触发超时。
  • 表面现象 — 运维看到的是 N 个 rank 同时报 NCCL TIMEOUT 错误，日志里全是 "Watchdog caught collective operation timeout"，根本分不清谁是根因。
  • 这就是传播性 — 1 个 rank 的硬件故障，"传染"成 N 个 rank 的超时错误。如果不做根因分析，每次故障都要人工排查几百条日志。

RAS 定位根因的五层机制

第一层：硬件信号采集 — 直接看"谁的硬件坏了"

  • 不依赖 NCCL 超时 — RAS 直接读取底层硬件诊断信息，这是最可靠的信号源。
  • NIC 健康状态 — 网卡固件报告的链路状态（Link Down / Degraded）、错误计数器（CRC error、packet drop rate）。
  • NVLink 错误计数器 — NVLink 硬件报告的 replay count、recovery count，异常升高说明链路不稳定。
  • PCIe AER（Advanced Error Reporting）— 总线层的不可纠正错误，直接指向哪个设备有物理问题。
  • GPU Xid 错误 — NVIDIA 驱动报告的 GPU 异常（如 Xid 74 = NVLink error，Xid 79 = GPU fallen off the bus）。
  • 定位粒度 — 可以精确到具体哪个 rank 的哪个 NIC 端口 / 哪条 NVLink。

第二层：时序分析 — "谁先报错谁是根因"

  • 每个 rank 的错误时间戳被记录：第一个报错的 rank 大概率是根因，后续大批量同时超时的是传播受害者。
  • 硬件错误 vs 超时错误 — 根因 rank 报的是硬件级错误（如 ncclSystemError），受害 rank 报的是超时错误（ncclTimeout），两者类型不同。
  • 时间窗口判定 — 在 NCCL_TIMEOUT 时间窗口（默认数秒）之前报错的 rank 是嫌疑对象，窗口触发后才报错的基本是受害者。

第三层：拓扑感知 — 验证"故障传播路径是否匹配"

  • NCCL 知道完整的通信拓扑（Ring / Tree / NVLS 结构），可以推算故障从根因 rank 向外传播的预期路径。
  • Ring 场景举例 — 如果 Rank 1 是根因，那么 Rank 0（Rank 1 的上游，发数据给 Rank 1 会卡住）和 Rank 2（Rank 1 的下游，等 Rank 1 的数据会饿死）应该是最先受影响的。RAS 验证实际报错模式是否符合拓扑预期。
  • Tree 场景 — 如果故障节点是某个子树的根，那么整个子树的节点都会受影响，但其他子树不受波及。这种"局部受影响"的模式可以反推根因位置。

第四层：Straggler 检测 — "没坏但变慢了"

  • 不是所有问题都是"挂了" — 有些 rank 没有故障，但性能严重退化（Straggler），同样会拖慢整个集合操作。
  • RAS 监控每个 rank 的完成时间分布 — 如果某个 rank 的 P99 延迟持续偏高（如其他 rank 的 2 倍以上），标记为 Straggler。
  • 常见原因 — NIC 降速（如 400G 降到 200G）、GPU 降频（散热问题）、HBM ECC 纠错过于频繁、PCIe 链路降级。
  • 应用可据此主动 Shrink — 在 Straggler 拖垮整体性能之前，提前将其剔除。

第五层：心跳与带外健康检查 — "主动探测而非被动等待"

  • 周期性心跳消息 — 检测节点是否存活，不依赖数据面操作触发。
  • 带外通信通道（out-of-band） — 不走 NCCL 的数据路径（如走 TCP），避免被数据面故障阻塞导致"检测通道和数据通道一起挂"。
  • 区分硬件故障 vs 软件崩溃 — 心跳丢失但硬件信号正常 → 可能是进程 crash 而非硬件坏了，恢复策略不同。

能否定位到具体哪个 Rank？— 能，但有边界

可以精确定位的场景

  • 硬件故障明确时 — NIC Link Down、GPU Xid error、NVLink replay count 暴涨等硬件信号直接绑定到具体的物理设备，而每个设备对应一个确定的 rank。这种情况 RAS 可以精确到 rank + 故障组件（如 "Rank 5 的 NIC 端口 1 链路断开"）。
  • Straggler 场景 — 通过性能指标对比，可以精确识别哪个 rank 拖后腿。
  • 进程崩溃 — 某个 rank 的进程退出 / 被 OOM kill，通过心跳 + 进程状态直接定位。

定位有模糊性的场景

  • 交换机故障 — 如果是 NVSwitch 或 IB 交换机坏了，多个 rank 同时受影响，RAS 可以缩小范围到"经过这个交换机的所有 rank"，但无法指向单个 rank（因为根因不在 rank，在网络设备上）。
  • 间歇性错误 — 偶发的 bit flip、瞬时链路抖动等，可能在故障复现前已经恢复，RAS 只能记录历史事件供事后分析。
  • 软件 bug 触发的死锁 — 如果是应用逻辑导致某些 rank 没有参与集合操作（如控制流 bug），RAS 可以发现"谁没参与"，但无法判断这是 bug 还是故意行为。

从 Communicator 到 Rank 的信息传递

  • ncclCommGetAsyncError() — 每个 rank 可以查询自己所在通信器的错误状态，但返回的是通信器级别的状态（有错 / 无错），不直接告诉你"是谁引起的"。
  • RAS 信息查询 — RAS 子系统可以提供更丰富的诊断信息，包括哪些 rank 被标记为故障 / Straggler，这些信息通过 RAS API 暴露给应用层。
  • 应用层决策流程：RAS 报告 "Rank 5 硬件异常" → 应用调用 ncclCommRevoke() 作废当前通信器 → 调用 ncclCommShrink() 时传入排除列表 [Rank 5] → 用剩余健康 rank 重建通信器。
