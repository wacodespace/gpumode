从 PTX/SASS 中学习的四种实用方法

1 / 访存宽度

数据搬运是否被加宽了？

向量化拷贝路径是最直接的观察入口：源码写的是 copy，SASS 能揭示实际走的是标量搬运还是 128-bit 宽向量搬运。

LDG.E R3, desc[UR4][R2.64]
STG.E desc[UR4][R4.64], R3

LDG.E.128 R8, desc[UR4][R4.64]
STG.E.128 desc[UR4][R2.64], R8
2 / Warp 集体行为

线程之间是否正确协作？

ldmatrix 能揭示一个 warp 如何集体地将矩阵片段从 shared memory 搬入寄存器，为 MMA 运算做准备。

ldmatrix.sync.aligned
  .m8n8.x4.shared.b16

3 / 指令选择

DSL 是否生成了正确的运算？

如果 lowering 过程插入了可避免的类型转换，内联 PTX 可以更直接地表达硬件运算。

fpext bf16 -> f32
asm "tanh.approx.f32"
fptrunc f32 -> bf16

asm "tanh.approx.bf16"

总结与理解

这四个视角的内在逻辑

四个问题是按抽象层级递进排列的

第 1 个问题（访存宽度）是最"机械"的检查——看一条 load/store 指令的位宽后缀就行。第 4 个问题（架构编排）则需要理解整个 Hopper 执行模型：warpgroup 是什么、TMA 描述符怎么配、mbarrier 怎么协调流水线。

这个递进是有意设计的：你可以从第 1 层开始获得收益，不需要一上来就理解完整的架构执行模型。

前两个看 SASS，后两个看 PTX（或两者都看）

问题 1（LDG.E vs LDG.E.128）和问题 2（ldmatrix）展示的是 SASS 级别的指令——这是硬件真正执行的东西。问题 3 和 4 则更多涉及 PTX 层面的选择（inline asm、WGMMA），因为这些决策发生在编译器的前端/中间层。实际排查时两层都会看，但每个问题有一个更自然的"入口层"。

问题 3 是 inline PTX 的正面用例

上一张 slide 警告了 inline PTX 的风险，这里展示了它的价值。例子很具体：tanh.approx.f32 需要先 fpext bf16 → f32 再 fptrunc f32 → bf16，两次类型转换是编译器 lowering 引入的开销。而 tanh.approx.bf16 直接在 bf16 上算，跳过了两次不必要的精度转换。这就是"DSL 没给你最好的指令选择"的典型场景——你通过读汇编发现了问题，再通过写 inline PTX 绕过它。

问题 4 本质上是在问"新硬件特性是否真的被使用了"

每一代 GPU 架构都引入新的执行路径（Ampere 的异步拷贝、Hopper 的 TMA 和 WGMMA）。框架和库的文档可能声称"支持 Hopper"，但实际编译产物里有没有出现 WGMMA、TMA、mbarrier 这些指令，是唯一的硬证据。如果你在 H100 上跑 kernel 却看不到这些指令，说明你的代码走的还是上一代的执行路径——性能天花板可能就差在这里。

一个实用的排查思路：从简单到复杂

这四个问题可以作为一个快速的 kernel 审计清单。按顺序过一遍，每一步都是独立的 pass/fail 判断：

① 访存宽度
看到 .128 了吗？
SASS · 5 秒
② Warp 协作
ldmatrix 在吗？
SASS · 10 秒
③ 指令选择
有冗余类型转换吗？
PTX · 1 分钟
④ 架构路径
WGMMA/TMA 落地了吗？
PTX+SASS · 2 分钟

注意时间估算：前两个是 grep 级别的操作（搜一个指令后缀或助记符），后两个需要稍微理解上下文。但即使是最复杂的第 4 个问题，也不要求你读懂整个 kernel 的汇编——你只需要确认特定指令的存在与否。
