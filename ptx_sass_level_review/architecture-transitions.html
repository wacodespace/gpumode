总结与理解

这张 slide 的核心信息

三张卡片是三个不同粒度的"漂移"

第一张讲的是代际跨越（Ampere → Hopper）：整个编程模型都变了，从"每个 warp 独立算"变成"warpgroup 协调执行"。这不是换个 opcode 的问题，是执行哲学的改变。

第二张讲的是编译器后端的漂移（Hopper → Blackwell）：同一份 PTX 给不同后端编译，产出的 SASS 结构可能完全不同。编译器的指令选择、调度策略都会随 target 改变。

第三张讲的是同代内的 sub-target 差异：即使都是 Blackwell，SM100 和 SM100a 可能走不同的指令路径。这个粒度是最容易被忽略的。

"不要过度解读单条 opcode" 是一个关键警告

Slide 第二张卡片特意强调了这一点。这里说的是跨代命名漂移：同一代架构内，HMMA（warp 级）和 HGMMA（warpgroup 级）是不同的硬件操作，看到 HMMA 就是没用 warpgroup。但跨代时，相同执行粒度的操作可能换了完全不同的名字——比如 Blackwell 上的 tcgen05.mma 对应的可能就是 warpgroup 级别的执行，只是不再叫 WGMMA。因此不能仅凭"没看到某个指令名"就下结论，要看整体拓扑：数据搬运路径、同步结构、寄存器分布是否符合目标架构的原生执行模式。

PTX 的"可移植性"在这里暴露了它的局限

PTX 的设计初衷是"写一次，跨架构运行"——一份 PTX 编译到 Ampere、Hopper、Blackwell 都能跑。但这张 slide 指出的恰恰是：能跑不等于跑得一样。ptxas 为不同 target 选择的指令序列、调度方式、同步策略可以完全不同。PTX 提供了可移植性（portability），但没有提供执行一致性（execution determinism）。

第三张卡片暗示了一个实际的工作流问题

"same kernel, same library, different emitted path" 说的是：你可能从某个 benchmark 博客上看到"Blackwell 上这个 kernel 的 SASS 用了 XXX 指令"，但你自己编译出来的 SASS 完全不一样。原因可能是你们用了不同的 sub-target（sm_100 vs sm_100a）、不同版本的 CUDA toolkit，甚至不同的 ptxas 优化等级。在 Blackwell 这种还在演进中的架构上，别人的编译产物不能直接作为你的参考——必须看自己的。

旧指令到底怎么"变成"新指令的？——不是替换，是重构

直觉上会觉得"mma.sync 升级成了 WGMMA"、"cp.async 升级成了 TMA"。但实际上这不是一对一替换——中间隔着编译器的一系列结构性决策。

关键问题：编译器中间那一步不是确定性的。同一份 PTX 里的 mma.sync，编译器给 Hopper target 编译时可能产生三种结果：
完全升级
WGMMA + TMA + mbarrier 流水线全部落地
部分升级
用了 WGMMA 但搬运还是走 cp.async 老路径
完全回退
某些约束没满足，回退到 per-warp HMMA

你心里预期的是"Hopper 原生路径"，但编译器实际给你的可能是混合体甚至完全回退。不看编译产物，就不知道 lowering 漂到了哪里——这就是"compiler-target drift"的含义。

架构漂移的五个层次

同一份源码，经过下面五个阶段，每一步都可能因为 target 不同而发生分歧：

源码
完全相同
PTX
可能相同
指令选择
可能不同
调度/寄存器
很可能不同
运行时行为
几乎一定不同

这就是为什么 slide 的结论是"审计 target-native 路径至关重要"——你不能假设源码相同就意味着执行路径相同。每换一个目标架构（甚至 sub-target），都值得重新检查编译产物。
