内联 PTX 注意事项

编写 PTX 有独立的失败模式

编译器前端无法完全理解内联 asm 模板字符串；无效的 PTX 可以通过源码编译，但会在 ptxas 或 JIT 加载时失败。

Kernel 生成

当代码是生成的时候，这更重要

如果 agent 或 DSL 编写了 kernel，那么检查生成的汇编结构是少数能从硬件层面验证优化是否真实生效的手段之一。

总结与理解

这张 slide 在说什么？

核心论点：读和写是完全不同的技能

就像你能看懂 X 光片不意味着你要当放射科医生一样。读 PTX/SASS 是模式识别——你在寻找特定的信号（tensor core 指令出现了吗？有没有 spill 到 local？同步结构对吗？），而不是从零开始用汇编写程序。slide 反复强调这一点，是为了降低心理门槛：你不需要"精通汇编"，你只需要学会"看懂编译器给了你什么"。

为什么这件事不能跳过？

高层框架（Triton、CUTLASS、JAX）承诺性能，但抽象层会隐藏实际发生的事情。你写了 tl.dot()，你以为它用了 tensor core，但编译器可能回退到了 FMA 循环。唯一确认的方式就是往下看一层：PTX 里有没有 mma.sync？SASS 里有没有 HMMA？如果没有，你的"优化"就是假的。

Inline PTX 的警告值得特别注意

Slide 单独把这一条标红，是因为它有一个反直觉的陷阱：写内联 PTX 时，nvcc 前端不会真正解析 asm() 里的字符串内容。这意味着你写了语法错误的 PTX，编译阶段不会报错，一路绿灯直到 ptxas 或运行时 JIT 才炸。这跟"读"汇编不同——"写"汇编有一个编译器帮不了你的盲区。

AI 时代让这件事变得更重要

当 LLM 或代码生成 agent 帮你写 kernel 时，生成的代码可能语法正确、能编译通过，但产生的汇编结构完全不是你期望的。检查生成的 PTX/SASS 是为数不多的硬件层面 ground truth 校验。这也是 slide 最后一张卡片单独强调 "kernel generation" 的原因——它不只是理论问题，而是一个正在发生的实际工作流问题。

实践心智模型：你需要的不是"读懂每一条指令"，而是"知道去找什么"
