总结与理解

这张 slide 补充了上一张（NCU vs PTX/SASS）遗漏的关键维度

核心论点：NCU 没有"预期"这个概念

NCU 测量的是实际发生了什么——它能告诉你 tensor core 利用率是 30%，local memory traffic 是 2GB/s，stall 主要是 memory dependency。但它不知道你期望这些数字是多少。

你期望 tensor core 利用率是 90% 还是 30% 就够了？你期望有 local memory traffic 还是完全没有？这些"预期"存在于你的源码意图里，不存在于 profiler 的输出里。只有你自己（借助 PTX/SASS 审查）能判断"实际 vs 预期"之间的差距。

三列布局揭示了一条"意图漂移链"

从左到右是一条因果链：你的源码表达了意图（用 tensor core、走 shared memory、目标是 sm_90a）→ 编译器在 lowering 过程中可能偏离意图（寄存器分配不够、指令选择回退、同步插入不当）→ 最终二进制包含的可能不是你要的东西（older MMA form、同步搬运代替异步搬运、st.local 溢出）。

问题在于：左列和右列之间没有直接的可见关系。你看源码觉得"没问题"，看 profiler 觉得"有问题"，但连不上。PTX/SASS 是中间那座桥。

左列的四个标签是一份"源码意图检查清单"

Slide 列出了四个你在写 kernel 时隐含的假设：

算术——我期望用 tensor core（WGMMA），不是标量 FMA。
内存——我期望通过 shared memory 做 tiling，不走 global 直读。
目标——我指定了 sm_90a，期望编译器使用 Hopper 原生路径。
状态——我没有写任何 local memory 操作，不期望有 spill。

每一条假设都可能在 lowering 中被违反——而且违反之后源码层面看不出任何异常。

底部的 NCU 五指标恰好是"症状，不是病因"

Stall = 症状（有等待）、Local Traffic = 测量开销（有搬运）、Tensor Use = 利用率（低或高）、Occupancy = 运行时状态、Latency = 影响（慢了多少）。这五个都是结果，不是原因。

对应的"病因"在 PTX/SASS 里：Stall 可能因为 barrier shape 不对；Local Traffic 因为 st.local/ld.local 溢出；Tensor Use 低因为用了 HMMA 而非 WGMMA；Occupancy 低因为寄存器分配过多；Latency 高因为同步搬运替代了异步 TMA。

从意图到测量的三段链：每一段都可能断

→漂移？

寄存器分配 / 指令选择 / 同步插入
→回退？
实际二进制
HMMA? st.local? scalar load?

NCU 站在链条的最右端，测量最终的执行效果。但它无法告诉你断在了哪一段——是你的源码意图本身就有问题？还是编译器 lowering 偏离了？还是目标架构后端选择了一条非预期路径？

PTX/SASS 审查让你能区分这三种情况——这是 NCU 做不到的事。当 NCU 说"tensor core 利用率低"时，PTX/SASS 告诉你："因为编译器选择了 HMMA 而不是 WGMMA"（lowering 漂移）或"因为目标后端是 sm_80 而非 sm_90a"（target 问题）或"因为你的 tile size 太大导致寄存器溢出"（源码意图问题）。
