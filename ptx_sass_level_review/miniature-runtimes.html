瓶颈往往在于生成的执行路径是否高效地协调了拷贝引擎、tensor 引擎、内存分阶段、barrier 和 store 操作。

Mega-kernel 让这件事更重要

融合和生成的 kernel 越来越像微型运行时——带有显式控制平面来管理本地存储、异步引擎、tensor 引擎和集群级调度。

PTX/SASS 是微型运行时变得可检查的地方。
总结与理解

从"一段计算"到"一个调度系统"

"微型运行时"这个比喻非常精确

传统的 kernel 就是一段计算代码——读数据、算、写回。现代 Hopper/Blackwell 上的高性能 kernel 更像一个小型操作系统：它有自己的"进程"（producer warp 和 consumer warpgroup），有自己的"IPC 机制"（mbarrier），有自己的"内存管理"（shared memory 的分阶段使用），有自己的"I/O 子系统"（TMA 拷贝引擎）。

这些组件的协调质量决定了性能，而不是某一条指令的吞吐量。

五个控制平面 = 五个可以独立出错的维度

Slide 左侧列出的五个平面不是装饰性的分类，而是五个独立的检查维度。每个平面都可能出问题：

拷贝平面——用了 TMA 还是回退到了线程级拷贝？
同步平面——mbarrier 阶段划分正确吗？arrive/wait 配对了吗？
张量平面——用了 WGMMA 还是回退到了 HMMA？
内存平面——有没有意外的 local spill？
控制平面——producer/consumer 分工是否落地？

"FLOPs 充裕，协调稀缺" 是整个 slide deck 的主题句

现代 GPU 的 tensor core 算力已经远远超过了大多数 kernel 的需求。H100 的 FP16 峰值是 ~2 PFLOPS——瓶颈几乎不可能是"算得不够快"。真正的瓶颈是：数据能不能及时喂到 tensor core？搬运和计算能不能重叠？同步有没有引入不必要的等待？

这就是为什么汇编审查的重点从"看有没有用对的算术指令"转向了"看协调结构是否高效"。

Mega-kernel 把这个问题推到了极端

Kernel fusion（将多个操作融合成一个 kernel）是当前最重要的优化手段之一。但融合之后的 kernel 变得更像一个微型运行时：它需要管理更多的 shared memory 阶段、更复杂的 producer/consumer 流水线、更多的 barrier 同步点。

如果你用的是 Triton 这样的编译器，或者 AI agent 生成的融合 kernel，你面对的不是"一条指令对不对"的问题，而是"整个调度拓扑是否合理"。这只能通过检查 PTX/SASS 来判断。

新旧 kernel 的本质区别

从"计算核心"到"微型运行时"的转变，可以用这张表来概括：

维度传统 Kernel（Ampere 及之前）现代 Kernel（Hopper / Blackwell）
核心抽象 一段计算代码 一个带调度的运行时
性能瓶颈 算术吞吐 + 访存带宽 协调效率 + 流水线利用率
数据搬运 线程各自搬（cp.async） 硬件引擎搬（TMA），与计算重叠
计算单元 Per-warp MMA Warpgroup MMA（4 warp 协作）
同步机制 bar.sync（简单栅栏） mbarrier + arrive/wait（流水线阶段）
角色分工 所有 warp 做同样的事 producer warp 搬数据，consumer warpgroup 算
汇编审查重点 有没有用对指令？有没有 spill？ 调度拓扑对吗？流水线跑起来了吗？

Slide 底部的结论一句话总结了这一切：PTX/SASS 是这个微型运行时变得可检查的地方——源码层你看到的是高层 API 调用，只有在汇编层，这些协调结构才以可审计的形式暴露出来。
