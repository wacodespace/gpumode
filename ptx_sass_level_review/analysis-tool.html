不是 Profiler

它不告诉你"这个 kernel 跑了多久"——它告诉你的是编译器生成了什么：用了哪种 MMA、有没有 spill、搬运是标量还是向量。这些事实在你跑 profiler 之前就已经写在二进制里了。

不是编译器

它不会重写 kernel；它缩小工程搜索空间，告诉你应该关注什么。

可 Diff 的产物

分析结果可以跨 target、跨编译器版本、跨编译选项、跨生成候选进行比较。

这个工具把反汇编转化为排序的、有证据支撑的假设——告诉你下一步应该测量和检查什么。
总结与理解

从"看汇编"到"分析汇编"的工程化跨越

四步流水线把"读汇编"变成了可重复的工程流程

前面所有 slide 讲的都是"为什么要读 PTX/SASS"和"读什么"。这张 slide 终于回答了"怎么规模化地读"。四步流水线的设计很清楚：

收集——从编译产物中提取 PTX 和 SASS（cuobjdump、nvdisasm）。
解析——把文本形式的汇编变成结构化数据（指令、操作数、地址空间、寄存器）。
检测——在结构化数据上跑模式匹配（有没有 spill？用了哪种 MMA？搬运是标量还是向量？）。
排序——按严重程度排列发现，产出一份可操作的报告。

这四步把"人类盯着汇编找问题"变成了"工具自动扫描 + 人类审核结果"。

三个边界声明定义了工具不做什么

这三张边界卡片是工具设计中最聪明的部分——清楚地画了三条线：

不是 profiler：工具不会告诉你"这个 kernel 跑了多少毫秒"。它只说"这个 kernel 的编译产物里有 st.local，这可能是个问题"。性能结论留给 NCU。

不是编译器：工具不会自动修复问题。它告诉你"编译器选了 HMMA 而不是 WGMMA"，修改策略是你的事。它缩小搜索空间，不替代决策。

可 diff：这是工具最具工程价值的特性——分析结果是结构化的，可以跨版本比较。改了一行源码，重新编译，diff 一下分析结果，就知道编译器的决策变了没有。

"排序的、有证据支撑的假设"——不是结论，是假设

底部那句总结特意用了"hypotheses"而不是"conclusions"。这个用词揭示了工具的哲学：静态分析不能证明性能问题，只能提出假设。

看到 st.local/ld.local 不等于"性能一定差"——如果那段代码不在热路径上，spill 可能完全不影响性能。看到 HMMA 而不是 WGMMA 不等于"一定要换"——可能问题的 tile size 就是不适合 warpgroup 操作。

工具产出的是带优先级的审查清单，最终判断还是需要 profiler（NCU）来验证。这和前面 slide 的观点完美闭合：PTX/SASS 提假设，NCU 验证假设。

四个使用场景覆盖了 GPU kernel 开发的完整生命周期

subtitle 列出了四个场景，每个对应一种不同的使用模式：

Kernel 开发——手写 kernel 时，编译完跑一次分析，确认编译器的决策符合预期。
生成式 kernel——AI agent 或搜索循环生成的候选 kernel，用分析工具做自动化过滤（上一张 slide 的 oracle）。
架构迁移——从 Ampere 迁到 Hopper 时，diff 两个 target 的分析结果，看哪些路径变了。
CI 回归——每次 commit 都跑一次分析，确保编译产物没有意外回退（新 spill、指令降级）。

这张 slide 是整个 deck 的落地方案：前面所有的观察、分析、警告，最终指向一个可操作的工具。它不是万能的——不替代 profiler，不替代编译器，不替代人类判断。但它填补了一个关键空白：让编译产物审查从"专家手工活"变成"工程化流程"，使得这种审查可以自动化、可规模化、可集成到 CI/CD 流水线中。
