NCU 剖析运行时，PTX/SASS 审计 Lowering。

目的不是替代测量，而是解释测量到的开销是由什么造成的。

问题 NCU / Profiler PTX/SASS 审查 为什么重要
Kernel 慢吗？ 能回答：timing、stall、occupancy、带宽、tensor 利用率。 不能回答：静态结构无法证明运行时开销。 NCU 是测量权威。
开销来自哪里？ 间接：通过症状和指令/计数器混合推断。 直接：opcode、地址空间、向量宽度、barrier、spill、回退路径。 这是源码和测量之间缺失的那一层。
原生路径落地了吗？ 间接：低利用率或管线压力可能暗示。 直接：查找 WGMMA、HGMMA、HMMA、UTMALDG、ARRIVES。 架构迁移需要 target-path 审计。
Local 流量是 spill 路径吗？ 展示 local-memory 流量和性能影响。 展示 st.local/ld.local 或 STL/LDL，以及在 kernel 中的位置。 静态证据定位编译器/lowering 产物。
NCU 测量执行在哪里付出了代价。PTX/SASS 审查帮助解释是哪些生成的结构造成了那个代价。
总结与理解

两个工具回答不同的问题

NCU 回答 "What"，PTX/SASS 回答 "Why"

NCU（Nsight Compute）告诉你发生了什么：这个 kernel 跑了多久、哪个管线饱和了、occupancy 多少、带宽利用率多少。但它不能告诉你为什么会这样——为什么 tensor core 利用率只有 30%？为什么 local memory 流量这么高？

PTX/SASS 审查填补这个空白：tensor core 利用率低可能是因为编译器回退到了 HMMA 而非 WGMMA；local memory 流量高是因为寄存器溢出生成了 st.local/ld.local。原因直接写在汇编里。

表格第一行是最重要的边界声明

"Kernel 慢吗？"这个问题 PTX/SASS 回答不了。你不能看着一段汇编就说"这很慢"——因为静态结构不等于运行时行为。一段看起来有 spill 的代码可能因为 cache 命中率高而跑得很快；一段看起来很干净的代码可能因为 bank conflict 而很慢。

性能判断的权威永远是 profiler。PTX/SASS 的价值在于：当 profiler 告诉你"这里慢了"之后，帮你找到造成慢的那条编译器决策。

"缺失的那一层"是这张 slide 的核心观点

在没有 PTX/SASS 审查的工作流里，你有两端：源码（你写的）和 profiler 数据（你量的）。中间有一个黑盒——编译器做了什么决策？你只能猜。

PTX/SASS 打开了这个黑盒。你看到 NCU 报告 local memory traffic 很高 → 查 SASS 发现大量 STL/LDL → 定位到编译器把某些寄存器 spill 到了 local → 回到源码调整 tile size 减少寄存器压力。这条从测量到修复的路径，没有中间那层就断了。

第三行揭示了架构迁移的实际工作流

当你把 kernel 从 Ampere 迁移到 Hopper 时，NCU 可能显示"tensor core utilization 很低"。但这个信息不够：是因为没用上 WGMMA？还是用了但流水线没跑满？还是数据搬运成了瓶颈？

只有看 SASS 才能直接确认：有没有 WGMMA/HGMMA 指令？有没有 UTMALDG（TMA）？有没有 ARRIVES（mbarrier 同步）？如果这些都没有，说明编译器根本没有使用 Hopper 原生路径。

实际的调优工作流：NCU 和 PTX/SASS 交替使用

两个工具不是二选一，而是一个循环里的两个步骤：

1. NCU 定位热点
哪个 kernel 慢？
2. SASS 诊断原因
编译器做了什么？
3. 修改源码/编译选项
调 tile / pragma / flag
4. SASS 确认改变
结构变了吗？
5. NCU 验证效果
性能提升了吗？

注意步骤 4——在重新跑 profiler 之前，先看一眼 SASS 确认编译器的决策确实改变了。否则你可能改了源码，但编译器的 lowering 没变，profiler 结果当然也不会变。这一步能省掉很多无效的 profiling 循环。
