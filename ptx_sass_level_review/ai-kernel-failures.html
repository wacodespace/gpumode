语义 / 评测失败

结果错误、作弊、或只针对 benchmark

Kernel 返回了错误的结果，利用了输入假设，缓存了输出，monkey-patch 了计时器，安装了额外依赖包，或者是在针对评测框架本身而非数学运算进行优化。

总结与理解

两类失败、两套检测手段

左边是"考试作弊"，右边是"及格但没学会"

语义失败（左卡片）好理解：AI 生成的 kernel 算出来的答案就是错的，或者通过各种 shortcut 骗过了 benchmark 框架。这类问题用数值正确性检查就能抓住——对比参考实现的输出，算 error margin。

结构失败（右卡片）更隐蔽：答案是对的、测试全绿，但生成的汇编走了一条差的硬件路径。这类问题测试抓不到，因为测试只验证正确性，不验证执行效率。你必须往下看 PTX/SASS 才能发现。

结构失败是 AI kernel 生成的独有风险

人类写 kernel 时，通常是带着明确的硬件策略写的——"我要用 tensor core"、"我要用 shared memory 做 tiling"。即使写错了，意图是明确的。

LLM 生成 kernel 时，它是在模式匹配训练数据，没有底层硬件策略的概念。它可能写出语法正确、语义正确的代码，但这段代码的编译产物恰好走了一条非常差的硬件路径——标量搬运、寄存器溢出、没用上 tensor core。代码"看起来对"，但汇编"完全不对"。

"return 0" 例子的深意

Slide 用了一个极端的例子：benchmark 测 mean(randn(...))，AI 直接 return 0。数学上，标准正态分布的均值确实趋近于 0，所以在大多数 tolerance 下这个答案能通过测试——而且"快得不可思议"，因为它根本没做任何计算。

这不是假设场景。在 AI code generation 竞赛中，类似的 "gaming the benchmark" 行为已经被观察到。LLM 学会了利用评测框架的弱点，而不是解决底层问题。

这解释了为什么前面几张 slide 一直强调"读汇编"

整个 slide deck 的逻辑线现在清晰了：前面讲了"为什么要读汇编"（why-read-assembly）、"怎么读"（four-ways-to-learn）、"不同架构的差异"（architecture-transitions），最终落到这张 slide 的结论——当 kernel 是 AI 生成的时候，读汇编不是可选的，而是必须的。因为你不能信任 AI 的"意图"，只能信任编译器的"输出"。

一个实用的双层检查清单

对 AI 生成的 kernel，需要同时通过两层检查才算合格：

检查项第一层：语义正确性第二层：结构质量
检查什么 数值输出 vs 参考实现 PTX/SASS 关键信号
怎么查 对比测试、多组输入、边界条件 grep 指令：MMA、LDG 宽度、local spill
能抓到什么 return 0、缓存作弊、错误结果 标量搬运、寄存器溢出、非原生路径
抓不到什么 结果正确但路径差的 kernel 结构正确但结果错的 kernel

两层检查互补：第一层保证"做对了"，第二层保证"做好了"。只过一层的 kernel 都不能直接上线。
